# Contributing to Vyact

Thank you for helping improve Vyact. Contributions of code, documentation,
translations, testing, design feedback, and issue triage are welcome.

## Before You Start

- Search existing issues and pull requests before opening a new one.
- Open an issue before starting a large change so the scope and approach can be discussed early.
- Keep pull requests focused. Unrelated changes should be submitted separately.
- Never include API keys, OAuth tokens, personal data, or generated user content.

Small bug fixes, tests, translations, and documentation improvements may be submitted directly without prior approval.

## Development Workflow

1. Fork the repository and create a branch from `main`.
2. Follow the existing project structure and coding conventions.
3. Add or update tests for behavior changes.
4. Run the relevant backend and frontend checks locally.
5. Open a pull request that explains the problem, solution, and validation.

The continuous-integration workflow runs backend tests, frontend linting and tests, and the frontend build for pull requests.

## Review Expectations

Maintainers review contributions for correctness, security, privacy, accessibility, maintainability, and consistency with the project roadmap. Review may take time because Vyact is independently maintained. A request for changes is an invitation to continue collaborating, not a rejection of the contributor.

Maintainers may close changes that duplicate existing work, introduce unsafe data handling, add unnecessary dependencies, or conflict with the local-first direction of the project. The reason will be documented in the issue or pull request.

## Bug Reports

Include:

- Operating system and Vyact version
- Steps to reproduce
- Expected and actual behavior
- Relevant logs with secrets and personal data removed
- Screenshots, when useful and safe to share

## Feature Requests

Describe the user problem, the proposed outcome, alternatives considered, and why the change belongs in Vyact. Implementation details are welcome but not required.

## Community Contributions

The public community roadmap includes a discussion board, real-time chat, and searchable support knowledge. Contributions to moderation tooling, internationalization, accessibility, deployment documentation, and community safety are especially welcome. See [COMMUNITY_ROADMAP.md](COMMUNITY_ROADMAP.md).

## Governance and Conduct

Project roles and decision-making are described in [GOVERNANCE.md](GOVERNANCE.md). All participation is governed by the [Code of Conduct](CODE_OF_CONDUCT.md).

## Security

Do not report vulnerabilities in a public issue. Follow [SECURITY.md](SECURITY.md) for private reporting.
